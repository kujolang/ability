# Repository hardening on November 25, 2026

The baseline was `4843d66` on `main`. The review covered the definition and receipt contracts, execution and replay, the SQLite and process service adapters, the fixture server, signed-registry verification, SDK digest parity, architecture boundaries, and package verification. The changes address two paths where callers could lose a reliable record of work that had already run.

- Ability generated a receipt ID before completion audit and generated another ID for the returned receipt. A custom ID factory could give the auditor and caller different IDs for the same invocation. The runtime now carries one ID through audit, response, and idempotency-persistence failure reporting. If the supplied clock moves backwards, completion remains at or after the start so that the runtime can report the actual outcome.
- The fixture server recorded keyed work only after awaiting a handler. Two approved requests could both run the handler. The server now reserves the key before dispatch, reports equivalent overlapping requests as in progress, and replays the terminal response. A handler failure is terminal because the handler may have already made a change. Idempotency scope uses a structured key, and replay checks the normalized principal.

The baseline passed `scripts/verify-release.sh`. Focused regression checks demonstrated the mismatched audit ID and overlapping fixture handler calls. The candidate checks exercise receipt correlation, one-time approval, a single handler call under overlap, and replay of both success and failure. The broader gates exercise cross-language fixtures, signed-registry policy, process isolation, SQLite contention and restart, downstream consumers, and Fence boundaries. The separate application assurance suite also exercises crash recovery and admission fencing. Verification used the local Kujo 1.10.0 runtime.
