# Local durable application services

`services.local_sqlite` implements the existing canonical audit, approval-consumption and keyed-idempotency callbacks. It does not supply policy, authenticate a human, choose an execution principal, or turn a host confirmation into a grant.

An operator provisions an application-owned SQLite path with `initialize_local_store`. Put the database and its WAL/SHM sidecars in a private directory, reject symlinks in application configuration, and never accept paths from model inputs. The service refuses absent stores and unknown `user_version` values during execution. The initializer is an operator operation, never a tool action. This local service trusts the OS user and database owner; it is not multi-user remote isolation.

`issue_local_approval(path, invocation, approval_id, nonce, approver, issued_at_ms, expires_at_ms)` must be called only after independently authenticated human approval of an application-resolved exact invocation. Supply cryptographically random IDs/nonces from the application. Grants last at most fifteen minutes. The canonical `approval_binding_digest` binds input, definition, identity, tenant and invocation; native validation remains authoritative. Consumption requires the exact stored grant bytes, unexpired state and an atomic unconsumed/unrevoked update. `revoke_local_approval` blocks unconsumed grants. No model-supplied grant is issued or accepted merely because it has valid shape.

`local_sqlite_services(path)` returns callbacks to merge with the application's policy and other services. Admission uses SQLite `BEGIN IMMEDIATE` and a unique canonical key. The runtime supplies the canonical key/request digests; this module does not redefine them. Conflicting requests fail, concurrent requests return in-progress, and completed requests replay validated original receipt bytes after a digest check. Completion must match the initially admitted invocation ID. No key is deleted or silently reset. Database/audit failures fail closed through canonical runtime failure semantics.

An interrupted `started` record remains in-progress indefinitely. The generic service cannot determine whether a business effect committed. Reconciliation must inspect authoritative business state before an application-specific recovery procedure. Never retry by deleting a row. Business effects and receipt completion are separate commits: this is not exactly-once execution, an atomic business transaction, or automatic crash recovery. A failed handler's receipt is also replayed rather than automatically re-executed.

Audit rows hold only phase, invocation ID and a digest commitment, not raw input, approval credentials or handler diagnostics. Approval rows hold the grant (without raw input); idempotency rows hold canonical receipts. Applications must keep credentials out of domain results and approver identity/claims, and own retention, encryption requirements, storage quotas and cleanup. No credentials are required by this module. Receipt hashes detect accidental/cross-record corruption; they do not authenticate data against a malicious database owner.

The runtime checks policy/input/approval validity before keyed replay. Consequently an expired approval may block replay through `execute_ability`; retrieve the original receipt through an authenticated evidence route instead of issuing a new execution. Existing runtime ordering is unchanged.

Tests cover missing/forged/revoked/altered approvals, exactly-once grant consumption, conflicts, persistent in-progress state, receipt corruption, eight competing OS processes, one resulting business write and original-receipt replay after restart. Both interpreter and VM paths are exercised. The test handler is an isolated SQLite business fixture; production business transactions remain application-owned.
